# SVC 优先 API 与全 ONNX 原生方案可行性分析

研究日期：2026-10-09。本文是 SVC API 支持计划的技术依据，不启动原生推理实现，也不扩大首轮 RVC 适配范围。

## 决策与约束

本轮优先通过通用 SVC SDK 调用外部引擎 API。这里的“外部”指 LMMS 进程之外，可以是本机服务，不等于必须上传云端。LMMS 负责独立 SVC 轨道、参数界面、前端分块、分块缓存、进度与 A/B 试听；后端负责模型及推理算法。

用户对未来原生方案的前提是**全 ONNX 化**。这是本项目的接受条件，不是所有原生程序在技术上都必须遵守的规律。本文按严格口径评估：推理算法链中的内容编码、F0 提取、特征检索、生成器及必要音频前后处理均须有 ONNX 图表达；文件读写、UI、任务调度及普通 DAW 播放不计入推理图。可以由多个 ONNX 图组成，但不能把 Python、Praat、WORLD 或 FAISS 的实际推理留在图外，却称为全 ONNX。

用自定义算子包装现有 C++ 算法仍然需要部署、维护该原生实现，不视为已经消除这项依赖。将来若需要放宽为 ONNX 与传统 C++ 混合，必须另行获得用户批准。

**暂缓的原因是完整链路转换、数值一致性和 Windows 部署验证的工作量，不是宣称这些模型无法导出。** RVC 生成器已有官方导出代码，RVC 的 RMVPE 实现已有 ONNX Runtime 路径，FCPE 也已有社区导出产物；单个组件可用不能直接证明整条链满足本项目的全 ONNX 要求。

## 各组件的证据与剩余工作

下表的“剩余工作”是依据第一方实现作出的工程评估，不是已经完成的 LMMS 实测结果。

| 组件 | 第一方证据 | 全 ONNX 原生方案需要解决的问题 |
| --- | --- | --- |
| HuBERT | [fairseq 官方 HuBERT 文档](https://github.com/facebookresearch/fairseq/blob/main/examples/hubert/README.md)提供不同规模检查点，使用 fairseq 加载。 | 固定目标检查点、特征层、归一化和输出维度，构造稳定导出入口；验证不同块长下的动态时间轴、padding、帧数与数值一致性。不能把 ASR 输出图直接当作 SVC 内容特征图。 |
| ContentVec | [作者仓库](https://github.com/auspicious3000/contentvec)提供官方 PyTorch 实现，并区分可直接由 fairseq 加载的 legacy 表征模块。 | 明确使用哪一代权重和模块，核对输出特征与目标生成器的约定。转换网络后仍要验证音频归一化、帧对齐和块边界；“支持 HuBERT”不能自动推导为支持所有 ContentVec 检查点。 |
| RVC 生成器 | [RVC 官方 ONNX 导出代码](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion/blob/develop/rvc/modules/onnx/export.py)已有导出路径，输入包含内容特征、F0、说话人和噪声，区分 v1/v2 特征维度，并声明时间动态轴。 | 这是生成器图，不是原始音频到最终音频的完整转换图。还需覆盖编码器、检索、F0、前后处理及不同模型版本，验证随机输入、采样率与输出长度。 |
| FAISS 特征检索 | [FAISS 官方说明](https://github.com/facebookresearch/faiss)将其定义为密集向量相似度搜索库，主要由 C++ 实现并提供 Python 包装及部分 GPU 算法。 | 直接链接 FAISS 可构成原生方案，但不满足本项目严格全 ONNX 条件。须针对实际索引类型实现图内检索和加权逻辑，验证召回及性能；改为全量距离加 TopK 也不能假定与已有近似索引等价，且可能增加内存和计算量。 |
| 音频 DSP 与运行时 | [PyTorch ONNX 文档](https://docs.pytorch.org/docs/2.14/onnx.html)说明导出、动态形状及验证接口；[ONNX Runtime DirectML 文档](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)列出算子、会话并发与形状方面的约束。 | 导出成功、ONNX 检查通过、目标执行提供器可执行、音频结果等价是四个不同验收层次。重采样、滤波、STFT/mel、插值及幅度处理均需明确图内实现；还须实测 CPU/GPU 复制、内存、变长块和 Windows 打包。 |

## 各种 F0 提取方式

本地当前 RVC API 的已声明选项为 `pm`、`rmvpe`、`fcpe`，实施时以 API 返回为准。以下 CREPE、DIO、Harvest 的研究仅解释技术取舍，不意味着本轮增加这些后端选项。当前后端契约以 `D:\AI-Tools\RVC20260718Nvidia50x0\rvc_api` 为参考标准，公开 RVC 上游能力不能覆盖本地 API 的实际声明。

| 方法 | 已有事实及来源 | ONNX 化难度与边界 |
| --- | --- | --- |
| `pm` / Praat / Parselmouth | [Parselmouth 作者说明](https://github.com/YannickJadoul/Parselmouth)明确直接访问 Praat C/C++ 实现。 | 它不是等待导出的神经网络检查点。一般原生接入可以复用传统算法；严格全 ONNX 则需重新表达相应音高分析、候选选择和轨迹处理，并对齐窗口、阈值、无声值与帧位置。不能把“已有 C++”误写为“已有 ONNX”。 |
| RMVPE | [RVC 官方 RMVPE 源码](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI/blob/main/infer/rmvpe.py)在对应设备路径下加载 `.onnx` 并使用 `DmlExecutionProvider`；同文件仍包含 mel 提取、帧补齐及局部加权音高解码。 | 已有网络的 ONNX 执行证据，不能宣称无法导出。剩余关键是把图外前后处理纳入全 ONNX 契约，并验证短块、padding、清浊音阈值、浮点精度和输出帧数；ONNX 网络运行不等于整个 F0 流程已脱离 PyTorch/NumPy。 |
| FCPE | [FCPE 作者仓库](https://github.com/CNChTu/FCPE)给出解码、清浊音阈值和输出插值参数；[社区导出者的模型卡](https://huggingface.co/gzivdo/fcpe-onnx/blob/main/README.md)记录了非官方 ONNX 转换、固定版本及 STFT 复数输出 shim。 | 社区导出是该转换存在的一手证据，不是 FCPE 官方兼容承诺。必须固定版本、确认实际参数是否可表达，并自行比较数值与静音行为；模型卡提到安静帧可能出现 NaN，不能未经验证直接接入。作者关于数值等价的说明不代替 LMMS 验收。 |
| CREPE / torchcrepe | [torchcrepe 维护者文档](https://github.com/maxrmorrison/torchcrepe)区分神经网络输出与 Viterbi、加权 argmax 解码，并提供周期性滤波和静音阈值处理。 | 网络导出只是一个阶段；完整 ONNX 链还需覆盖分帧归一化、所选解码器、滤波和静音处理。若只移植网络并更换解码规则，可能改变八度错误和音高连续性，不能声称等价支持。 |
| WORLD DIO | [WORLD 官方 DIO 接口](https://github.com/mmorise/World/blob/master/src/world/dio.h)直接接收波形、采样率及算法选项，输出时间位置与 F0。 | 属于传统信号处理实现，不存在把权重文件导出即可完成的路径。严格图内方案需要重表达算法及帧布局；如目标流程另有音高细化步骤，也须一并覆盖。 |
| WORLD Harvest | [WORLD 官方 Harvest 接口](https://github.com/mmorise/World/blob/master/src/world/harvest.h)同样提供波形分析和 F0 轨迹接口。 | 原生 C++ 实现可复用不代表已全 ONNX 化。图内重实现需要逐项验证候选筛选、轨迹、边界与无声段；不能因同属 WORLD 就用 DIO 的验证结果代替 Harvest。 |

这些方法的“难度”没有统一秒数或工期结论：具体成本取决于模型版本、算法配置、动态长度和目标硬件。本研究未执行导出、性能测试或试听，因此不提供未经测量的速度排名，也不把缺少官方导出脚本当成数学上不可转换。

## 为什么优先 API

以下是结合上述证据与本次需求作出的设计判断：

1. **先交付用户需要的 DAW 工作流。** 分块发送和接收、每块完成后替换对应时间区间、保留原始 A、渲染 B、独立增益和进度，都能由前端与通用 SDK 完成，不必先重建整个推理算法链。
2. **让能力随后端返回变化。** 引擎、模型、说话人以及额外参数由 API 描述；通用参数界面无需把某一代 RVC、某个 F0 或固定模型列表写死。先建立 SDK，再以当前本地 RVC API 标准实现适配器，职责更清晰。
3. **推理依赖与 LMMS 发布解耦。** API 模式允许后端保留其已验证的 Python、GPU 库和模型组合。模型更新无需同时把全套导出及执行提供器适配纳入 LMMS 发布前置条件。
4. **减少主进程中的推理故障影响。** 后端进程故障可以表现为分块请求失败，由 SDK 记录和恢复；它仍可能影响共享 GPU 资源，因此这不是“完全隔离”的承诺。

## API 模式也有成本

- 需要独立服务、地址和可选 Bearer token，服务不可用时不能执行新转换；已有有效缓存仍可用于播放。
- 编解码、上传、下载和缓存写入会增加时间与磁盘占用；远程服务还有网络延迟及音频传输问题，本机服务也存在数据复制成本。
- 当前本地 RVC 后端采用串行推理并在请求后卸载模型的行为，应由适配文档明确记录。每块一个请求会重复承担加载/卸载开销；10 秒强制分块不代表 10 秒内完成，也不能默认提高并发就会加速。后端模型常驻或批处理优化另列后续工作，不在首轮擅自修改。
- 分块文件请求属于渐进离线渲染，不是低延迟实时音频流。只能依据已接收且验证成功的块更新完成进度；后端没有块内进度时显示“正在转换”，不能伪造精确百分比。
- 块边界、输出时长偏差、重采样和参数变化导致的缓存失效依然需要前端处理。API 不会自动解决接缝或 A/B 时间对齐。

## 将来重新评估原生的门槛

此节是未来决策条件，不是本轮新增里程碑。

1. 用户另行批准原生工作范围，并固定支持的模型族、F0 方法、检索形式和全 ONNX 推理边界。
2. 全链路每个算法环节均有可复现的图产物和版本契约；不能隐含调用 Python 或用自定义算子外壳掩盖传统运行时依赖。
3. 与参考后端逐层比较内容特征、F0、检索结果和最终音频，覆盖静音、极短尾块、长音、分块接缝、不同采样率及多说话人；事先定义误差和试听接受标准。
4. 在目标 Windows CPU/GPU 配置上验证动态块长、峰值内存、取消和模型切换，记录完整转换耗时；确认所选执行提供器的算子支持及会话限制。
5. 完成模型及依赖分发条件核查、故障处理和与 LMMS 音频线程的隔离验证；涉及 GUI 的验收继续使用真实 Windows Qt 窗口。

因此，本轮采用 API 的理由是把成熟后端能力接入可验证的音频编辑流程，避免让“完整推理链全 ONNX 化”成为 SVC 轨道首版的前置工程。未来可重新评估原生，但本计划不承诺其已具备实施条件。
